## 1. 一句话现状

**固件已经开发完并烧进设备，唯一没验证的是"设备 → 接收服务"这条网络链路**，
它被公司 Wi-Fi 的客户端隔离挡住。换到家里网络，把 `url` 改成群晖地址就能测。

设备侧不需要再改代码。

## 2. 公司网络为什么不通（已实测，不必重查）

设备连 `iTV24` 拿到 `10.169.1.62`，Mac 是 `10.169.1.177`：

| 检查 | 结果 |
| --- | --- |
| SSID / 信道 / BSSID | 相同（channel 4、`e8:9f:80:6b:7e:1b`） |
| 子网 / 网关 | 相同（`/24`、`10.169.1.1`） |
| Mac → 设备任意端口 | **超时**（连没人监听的 9999 也超时，不是 refused） |
| `arp -an` | 始终没有设备的 MAC |
| 设备日志 | `errno=119 (EINPROGRESS)` = SYN 发出、无回包 |

结论：**AP 客户端隔离**。企业 Wi-Fi 默认开启，同 AP 下终端互相不可见。
这不是固件问题。所以家里网络（或群晖同网段）是必要前提，不是可选项。

另外，从公司出口连群晖 `hutu0043.dsmynas.com:44293` 的 80/443/5000/5001 全部超时，
代理返回 504。公司网对家宽高位端口大概率是封的，这个结论**在家无法复核**，仅供参考。

## 3. 家里电脑上的操作顺序

### 3.1 先确认群晖能被访问

```sh
# 在家里的电脑上（不要用公司网）
curl -sS -m 5 -o /dev/null -w '%{http_code}\n' https://hutu0043.dsmynas.com:44293/
```

- 能出 DSM 登录页（200/302）→ 端口映射是通的，继续 3.2
- 超时 → 端口映射或 DDNS 有问题，先修这个。44293 要映射到群晖的 8000

### 3.2 部署接收服务

按 [nas-deploy.md](nas-deploy.md) 第 2 节做。要点：

1. 代码目录放 `server/`（`server.py`、`Dockerfile`、`docker-compose.yml`）
2. `tokens.json` 从 `tokens.example.json` 复制，填 `77f452f8` 那台设备的 token
3. `./data` 必须是**群晖本地盘**的 bind mount，不能放 SMB/NFS 共享
4. `docker compose up -d`，日志应有 `loaded 1 device token(s)` / `listening on 0.0.0.0:8000`
5. 端口 8000 要对内网可达，并且 44293 映射到它

> **注意 `docker-compose.yml` 里那句「不要直接映射到公网」**：那份配置假设走
> FN Connect 中继。你这个 `host:44293` 看起来是路由器直接端口映射，也就是真的把
> 8000 暴露到公网。两种做法都行，但差别要清楚：
> - 直接映射：简单、可用，但 8000 会长期挂在公网上，只能靠 Bearer token 挡人。
>   务必**用 HTTPS**（证书套在群晖的反向代理上），别用明文 HTTP 传 token。
> - 走 FN Connect：不占公网端口，但要先验设计文档 7.1 那三项（中继是否要求登录态）。

### 3.3 设备配网

设备上**长按 OK 进配网**，手机连热点 `AIPassport-52f8`（无密码），
浏览器开 `192.168.4.1`，填：

| 字段 | 值 |
| --- | --- |
| Wi-Fi 名称 | 家里的 SSID |
| Wi-Fi 密码 | 家里的密码 |
| NAS 地址 | **只填协议 + 主机 + 端口，不带路径**，如 `https://hutu0043.dsmynas.com:44293` |
| Token | 与 `tokens.json` 里 `77f452f8` 对应的那串，两边必须一模一样的 |

保存后页面会轮询显示结果。设备日志 `got ip` 那行会打出它拿到的地址。

> 地址栏的格式校验只接受 `http(s)://host[:port]`，**带 `/` 路径会被拒**（返回 `bad_url`）。

### 3.4 验证

```sh
# 1. 服务端健康
curl -sS https://hutu0043.dsmynas.com:44293/healthz

# 2. 服务端日志看有没有收到设备请求
docker compose logs -f | grep -E 'PUT|Authorization'

# 3. 录音后看群晖上有没有落文件
ls -l <代码目录>/server/data/<日期>/
```

设备端按 OK 开始录音，30 秒后再按 OK 停止，停止时会立刻尝试上传。
串口日志应该出现 `round done ok=1`，而不是 `ok=0`。

## 5. 换网络后如果还不通，按 errno 定位

| errno | 含义 | 先查什么 |
| --- | --- | --- |
| 119 `EINPROGRESS` | SYN 发出、无回包（连接超时） | 两台机器之间根本不通：防火墙、端口映射、AP 隔离 |
| 113 `EHOSTUNREACH` | 没有到目标网段的路由 | 设备网关对不对，目标 IP 在不在一个网段 |
| 111 `ECONNREFUSED` | 主机到了，端口没人听 | 容器起没起、端口映射对不对 |
| 110 `ETIMEDOUT` | 被静默丢弃 | 中间设备（防火墙 / 中继）拦了 |
| `E200 域名解析失败` | DNS | 设备能不能解析那个域名；HTTPS 场景常见 |

`errno=119` 最容易误读：字面是"连接正在进行"，实际是 lwIP 里 `connect()` 超时。

## 6. 两个待你确认的问题（不影响继续）

1. **开机自动录音**：有一次上电后 12 秒自动开始录音，串口里没有任何按键事件。
   代码里录音只有 `BSP_BTN_OK` 的短按一条入口。可能是按键误触发（如设备放在包里
   压到），也可能有别的路径。需要你在场回忆一下当时有没有碰按键。
2. **缓存时长**：实测码率 13.85 kbit/s，3.6 MB 缓存约 **36 分钟**，不是设计文档原来
   写的 40 分钟。文档已按实测改正。断网时最多录 36 分钟（会记 E500 并停止）。

这些都在 `/tmp`，只存在于上一台机器：

- `/tmp/token_20261122.txt` — token 明文
- `/tmp/server_run_20261122/tokens.json` — 上一轮本机联调用的 token 表
- `/tmp/nvs_read_20261122/nvs.bin` — 设备 NVS 原始备份

token 已经在设备 NVS 里了。到群晖上按 3.2 重新生成或沿用都可，**只要设备配网页和
群晖的 `tokens.json` 两边一致**。
